본 문서는 `AGENTS.md`의 핵심 원칙을 뒷받침하는 상세 개발 프로토콜, KDS/kcsc2md 연동 세부 절차 및 협업 가이드라인입니다.

## 1. KDS 국가건설기준 및 kcsc2md 자산화 상세 연동 규약

### 1.1. 연동 자산 인벤토리
1. **고품질 마크다운 기준서 (`f:/PyProject/kcsc2md/output/kds_md/`)**:
   - 국토교통부 원본 HWPX와 1:1 수식 주입(`LaTeX`)이 완료된 분할 마크다운으로 설계식의 절대적 Ground Truth 기준입니다.
2. **추출 이미지 자산 (`f:/PyProject/kcsc2md/output/KDS_ImageExtracted/`)**:
   - HWP 원문에서 무손실 추출된 표준 배근도 및 다이어그램 이미지를 웹 UI 및 도움말 렌더링에 직접 연동합니다.
3. **공식 구조설계 예제집 (`f:/PyProject/kcsc2md/output/예제집/`)**:
   - 콘크리트학회/강구조학회 공인 예제집 마크다운을 단위 테스트(`tests/engine/`) 검증 벤치마크 데이터로 활용합니다.
4. **0.01s 초고속 KDS 조항 라우터 (`kds-inspector`)**:
   ```bash
   python ../kcsc2md/.agents/skills/kds-inspector/scripts/search_kds.py --code "14 20 10" --query "등가직사각형"
   ```
5. **HWPX 원본 수식/표 검증기 (`hwpx-inspector`)**:
   ```bash
   python ../kcsc2md/.agents/skills/hwpx-inspector/scripts/extract_formula.py --code "14 20 10" --keyword "alpha1"
   ```

### 1.2. 우선 치유(Patch-First) 및 Self-Healing 환류 프로토콜
- `AltDP_3rd` 엔진 개발 및 KDS 검증 중 마크다운 기준서의 수식/표 오탈자나 누락을 발견한 경우, `AltDP_3rd` 코드를 임의로 우회 수정하지 않고 먼저 `kcsc2md`의 Self-Healing 패치 도구(`patch_kds_md.py`)를 통해 원본 마크다운 자산을 영구 치유한 후 최신화된 기준을 반영합니다.

### 1.3. 0.1% 오차 무결성 검증 (Cross-Validation)
- 원본 Midas Design+ 계산 결과, `kcsc2md` 공식 예제집 해답, 신규 AltDP_3rd 엔진 계산치를 삼각 대조하여 **오차 0.1% 미만의 무결성**을 입증합니다.

### 1.4. Zero-Dependency 런타임 원칙
- `kcsc2md` 자산과 도구는 개발/검증/빌드 타임의 Ground Truth 레퍼런스로 활용하며, `AltDP_3rd`의 프로덕션 런타임 코드는 외부 파일시스템에 의존하지 않는 독립 파이썬 패키지를 유지합니다.

## 2. 요구사항 & 문서 라이프사이클 상세 규약

1. **요구사항 문서 생성 규칙 (경량화)**: 
   - 사용자가 채팅으로 메모형식의 요청사항을 전달하며 "요구사항 문서 만들어줘" 등을 요청할 때는 별도의 Implementation Plan 아티팩트나 구현 계획을 생성하지 않고, 오직 요구사항 정리 및 `요구사항/요구사항XX.md` 파일 생성에만 집중합니다. (일련번호는 `요구사항/@@OLD/` 마지막 번호의 다음 번호 부여)
2. **대규모 요구사항 사전 점검 및 하위 문서 세분화 제안 (Scope Partitioning)**:
   - 작업 범위가 다수 부재/모듈(3개 이상 레이어/파일 10개 이상 등)에 걸쳐 있어 구현 누락 위험이 높다고 판단되면:
     1. 사용자에게 대규모 구현에 따른 **누락 위험을 사전에 알리고 확인을 요청**.
     2. 단일 요구사항을 하위 문서(예: `요구사항XX-1.md`, `요구사항XX-2.md` 또는 명확한 독립 Phase)로 **세분화하여 단계별로 구분 진행할 것을 제안**.
3. **요구사항 전수 체크리스트 검증 의무 (Zero-Omission Verification)**:
   - 요구사항 문서 작업 시 문서 내 세부 항목과 검증 기준(Acceptance Criteria)을 1:1 체크리스트로 대조 검증하고 누락 0건 확인 후 완료 보고.
4. **명시적 요청 시에만 완료/아카이빙**:
   - 사용자 요청 시에만 `요구사항/` 파일을 `요구사항/@@OLD/요구사항XX-YYMMDD_HHMM.md`로 이동 및 아카이빙.
5. **README.md 일괄 업데이트**:
   - 중간에 임의 수정하지 않고 사용자 명시적 요청 시에만 일괄 갱신.
6. **기술 문서는 실시간 최신화**:
   - `docs/` 내의 기술 문서는 아키텍처/구조 변경 시 지속 동기화.

## 3. Goal 주도형 단계적 연속 구현 규약 (Goal-Driven Continuous Partitioned Execution)

### 3.1. 집중력 유지 및 토큰 효율성 극대화
- 사용자가 마스터 요구사항(예: `요구사항05`)을 통째로 `/goal`로 지정하여 전체 작업을 지시할 때, 에이전트는 단일 컨텍스트 폭주와 누락을 방지하고 토큰 효율성을 추구하기 위해 작은 단위로 분할된 하위 Phase 문서(`요구사항XX-1`, `XX-2` 등)를 순차적 실행 단위로 삼아 지속적으로 전체 구현을 완주합니다.

### 3.2. 단계별 무결성 자율 전진 (Phase-by-Phase Verification & Progression)
1. **정밀 구현**: 각 하위 Phase별로 지정된 파일과 컴포넌트만 정밀하게 구현/수정하여 컨텍스트 낭비를 최소화합니다.
2. **테스트 확인**: 해당 Phase의 Acceptance Criteria(1:1 체크리스트) 및 단위 테스트(`pytest`) 100% 통과를 확인합니다.
3. **자율 연속 진입**: 완료 즉시 다음 Phase로 중단 없이 자율 진입하여 마스터 요구사항의 모든 Phase가 끝날 때까지 연속 작업을 수행합니다.
4. **최종 종합 검증**: 모든 하위 Phase 완료 후 마스터 요구사항의 종합 수용 기준을 최종 전수 검증하고 완수 보고합니다.

## 4. 버그 수정 및 개별 이슈 대응 규약 (Bug Fix & Issue Resolution Protocol)

### 4.1. 1이슈 1Phase 원칙 (One-by-One Resolution)
- 버그 픽스 및 결함 조치는 원인 규명과 영향도 검증의 정확성을 위해 되도록 1가지 이슈마다 독립된 Phase(또는 독립 작업 단위)로 구별하여 구현 계획을 수립하고, 1가지씩 해결 및 동작 확인(`pytest`/UI 검증)을 완료합니다.

### 4.2. 복잡도 기반 묶음 처리 제한
- 복잡도가 매우 낮고 상호 연관성이 높은 경미한 버그의 경우 예외적으로 1~3개 정도를 한꺼번에 계획할 수 있으나, 원칙적으로는 개별 아이템으로 분리하여 순차 처리합니다.

### 4.3. 요구사항 내 버그 픽스 동일 적용
- 일반 기능 요구사항 문서 내에 버그 수정(Bug Fix) 또는 오동작 개선 항목이 포함되어 있는 경우에도 동일하게 적용하여, 하위 Phase 분할 시 독립된 실행 단위로 분리하여 계획하고 검증합니다.

## 5. 수퍼 파일 지양 및 엄격한 모듈화 규약 (Anti-Superfile & Strict Modularity Protocol)

### 5.1. 수퍼 파일(Superfile / God Object) 발생 엄격 금지
포팅 과정에서 단일 파일에 수백~수천 라인의 코드가 집중되는 거대 모놀리식 파일(Superfile)의 생성을 엄격히 금지합니다. 단일 파일의 비대화는 가독성 저하, 토큰 낭비, 회귀 버그 유발 및 유지보수 불가능의 주원인입니다.

### 5.2. 단일 파일 크기 상한선 (File Size Thresholds)
* **권장 기준 (Soft Limit)**: 단일 파일 당 **300라인 이하** 유지 권장.
* **최대 한계 (Hard Limit)**: 단일 파일 당 **500라인을 절대 초과하지 않음**.
* 500라인에 근접하거나 초과할 가능성이 있는 모듈은 즉시 하위 패키지 디렉토리(`__init__.py` 포함)로 승격하여 기능별 서브모듈로 분할.

### 5.3. 레이어별 단일 책임 원칙 (SRP) 분할 표준

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 수퍼 파일 방지 모듈화 아키텍처 (Modular Layer Decomposition)                          │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 1. Engine Layer (`src/engine/`)                                                        │
│    ├── models.py / schemas.py   : 데이터 입출력 Pydantic / Dataclass 모델 정의         │
│    ├── formulas.py / math.py    : KDS 기준 수식 및 순수 수치 계산 함수                 │
│    ├── beam.py, column.py 등    : 각 부재별 설계/검토 오케스트레이션 로직              │
│    ├── serviceability.py        : 처짐, 균열 등 사용성 한계상태 전용 검토기            │
│    └── seismic.py               : 특수/중간 모멘트골조 내진 상세 전용 검토기           │
│                                                                                        │
│ 2. Web Frontend Layer (`src/web/static/js/`)                                           │
│    ├── store/                   : 상태 관리 및 로컬스토리지 영속화 (`project_store.js`)│
│    ├── components/              : UI 위젯별 독립 모듈 (`form_*.js`, `resizer.js`)     │
│    ├── visual/vector/           : 부재별 SVG/Canvas 벡터 렌더러 (`vector_*.js`)        │
│    └── report/                  : 계산서 템플릿 및 포맷터 (`redcr_*.js`)              │
│                                                                                        │
│ 3. Report & API Layer (`src/report/`, `src/api/`)                                      │
│    ├── routes/                  : 부재 도메인별 분할 라우터 (`rc.py`, `steel.py` 등)   │
│    └── generator.py, exporter.py: Jinja2, Excel, PDF 전용 독립 익스포터                │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 5.4. 모듈 분할 및 리팩토링 체크리스트
- [ ] 하나의 파일이 2개 이상의 독립된 책임(예: 수치해석 + HTML 렌더링 + API 라우팅)을 가지고 있지 않은가?
- [ ] 파일 라인 수가 300~500라인 한계 내에서 유지되고 있는가?
- [ ] 반복되는 공통 유틸리티(수식 포맷팅, 단위 변환, SVG 기초 도형 등)는 `common/` 또는 `utils/`로 격리 추출되었는가?
- [ ] 신규 부재나 기능을 추가할 때 기존 거대 파일에 누적하지 않고 독립된 서브모듈 파일로 작성되었는가?
